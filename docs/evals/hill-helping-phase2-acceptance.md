# Hill 助人过程第二阶段验收报告

状态：通过

日期：2026-07-31

验收对象：

- [AI 版 Hill 助人过程产品契约 v1](../HILL_HELPING_PROCESS_PRODUCT_CONTRACT_V1.md)
- [Hill Helping Skills 第 6 版差距审计](./hill-helping-skills-v6-gap-audit.md)

本报告只验收产品契约，不表示运行代码已经具备 Hill 助人能力。

## 1. 验收结论

第二阶段通过，可以进入第三阶段“架构迁移与分批实施计划”。

通过原因：

1. 契约明确区分了慢聊与小记，没有把记录、长期记忆或用户隔离带入聊天改造。
2. Hill 第 6 版被转译为流动的探索、领悟、行动目标，不是固定三阶段状态机。
3. 契约定义了适用性、准备度、意图、技术、关系修复和下一轮反应的完整闭环。
4. 用户的意义解释权、行动决定权、暂停权和纠正权均为硬边界。
5. Safety、直接回答义务和 Conversation OS 的唯一计划汇总权没有被 Helping
   Logic 覆盖。
6. 契约能由同一组跨场景规则处理 24 个反例，不依赖为某一句用户输入增加专门
   路由。
7. 契约明确暴露了与当前冻结架构的冲突，并把解决冲突留给第三阶段，没有在
   第二阶段暗改代码。

## 2. 首轮未通过项与修正

首轮审查没有直接放行，发现并修正了四个契约缺口。

### 2.1 意图和技术可能漂移

观察：

- `HillHelpingPlan` 原先允许用任意字符串表达意图和技术。

风险：

- 后续实现仍可在 Prompt 或代码中发明 Hill 契约之外的方法，重新形成不可审计
  的方法混用。

修正：

- 增加封闭的 `HillIntention` 和 `HillSkill` 联合类型；
- 新增意图或技术必须重新经过产品契约评审。

结果：通过。

### 2.2 关系修复被错误要求提供准备度

观察：

- 普通 `applicable` 必填规则会让关系修复也必须选择探索、领悟或行动准备度。

风险：

- 用户指出 AI 误解时，系统可能一边道歉，一边继续分析或推进目标。

修正：

- `relationshipPriority=repair` 可以暂停 Hill 目标和准备度；
- 修复轮只能执行关系修复，等待下一轮用户反应后再选新目标。

结果：通过。

### 2.3 相邻话轮可能被误判为技术效果

观察：

- 原反应结构记录反应类型和证据，但没有先证明当前用户话轮确实在回应上一助人
  行动。

风险：

- 换话题、继续发消息或文字变长可能被错误归因于上一技术有效。

修正：

- 增加 `relationToPreviousMove`；
- 只有直接回应、延续或拒绝且有可追溯证据时，才允许形成影响判断；
- 换话题不证明有效或无效，关系不清时必须令 `impactKnown=false`。

结果：通过。

### 2.4 系统失败可能伪装成“不适用”

观察：

- 原契约没有区分“成功判断为 `not_applicable`”与“Helping Logic 没有成功
  运行”。

风险：

- timeout、schema 错误或 provider 失败可能被包装成普通陪伴回复，用户看到的
  是自然句子，但助人过程实际没有发生。

修正：

- 增加 `HillHelpingDecision`，把 `decided` 与 `failed` 分开；
- 失败不得伪装成 `not_applicable`；
- Conversation OS 不得在失败时自行补写 Hill 方法。

结果：通过。

## 3. 产品契约硬门

| 验收项 | 结果 | 证据 |
| --- | --- | --- |
| 方法基准 | 通过 | 明确采用 Hill 第 6 版，记录版本、出版信息和来源 |
| 产品边界 | 通过 | 仅覆盖慢聊；小记、长期记忆、用户隔离明确排除 |
| 非线性目标 | 通过 | 探索、领悟、行动可维持、切换、退出，不按轮次推进 |
| 适用边界 | 通过 | 每个非 Safety 话轮产生 applicable / uncertain / not_applicable |
| 助人闭环 | 通过 | 上一行动—当前反应—下一意图进入同一跨轮合同 |
| 关系修复 | 通过 | 修复可以暂停其他目标，且必须等待用户后续反应 |
| 领悟边界 | 通过 | 必须有准备度、证据、协作性、暂时性和可撤回性 |
| 行动边界 | 通过 | 提供选项、练习和小步骤，但不替用户决定 |
| 文化谦逊 | 通过 | 只使用用户明确材料，不从身份推定意义 |
| AI 身份边界 | 通过 | 排除虚构感受、经历、身体能力和专业资格 |
| Safety 优先级 | 通过 | Safety 可以覆盖普通助人过程 |
| 直接回答义务 | 通过 | 混合话轮不能以助人目标删除用户的明确问题 |
| 决策所有权 | 通过 | Helping Logic 拥有 Hill 领域判断；Planner 仍汇总唯一计划 |
| 失败语义 | 通过 | 运行失败与成功判断“不适用”严格分离 |
| 可评估性 | 通过 | 计划、已提交行动、反应和下一决策均有结构化证据 |

## 5. 现有架构基线验证

执行：

```text
npm run check:architecture-v1
npm run check:conversation-os-architecture
npm run check:conversation-os-control
```

结果：

- 三项检查全部通过；
- 当前生产决策汇总者仍为 `conversation_os.response_planner`；
- 当前普通聊天链路仍只产生一个 `ResponsePlan`；
- Validator 不能重规划；
- 现有 Clinical 仍是可选策略提供者；
- Conversation OS control 检查包含 20 个既有反例且通过。

这组结果不是 Hill 能力已经实现的证据。它确认了第三阶段必须解决的真实架构差距：

> 当前 Clinical 只有在 Conversation OS 先判断为部分支持场景时才被调用；目标
> 契约则要求所有非 Safety 话轮都产生可追踪的 Hill 适用性决定，并在最终
> `ResponsePlan` 形成前完成领域判断。

## 6. 未在第二阶段验收的内容

以下内容尚未实现，也不因本报告通过而被视为完成：

- 运行代码中的 `HillHelpingPlan`；
- `CommittedHelpingMove` 的持久化与加载；
- 下一轮用户反应评估；
- 探索、领悟、行动技术的实际生成；
- 真实模型轨迹评估；
- 线上灰度、性能、成本和部署。

这些内容必须按第三阶段计划分批实现，并在每一批之后单独验收。

第二阶段没有剩余契约阻塞。

允许进入第三阶段，唯一任务是制定架构迁移与分批实施计划；第三阶段本身仍不
授权修改运行代码。
