## 1. 范围与边界

本合同只覆盖批次 1.5 已存在的两个普通 Conversation OS 动作：

- `offer_emotional_support`
- `repair_previous_wording`

它不启用 Hill 目标或技术，不写入 `CommittedHelpingMove`，不进入批次 2，也不改变
Safety、直接回答、暂停、Grounding 和当前话题的既有优先级。

本合同解决的是“ResponsePlan 只给出动作名称和禁止项，却没有说明该动作必须完成什么
正向会话功能”的缺口。它不是回复模板，也不规定固定措辞。

### 1.1 普通承接门控补充（2026-10-12）

原合同范围与身份合同构成既有三个正向动作；普通承接此前只有 Surface 指导，缺少
绑定时语义校验直接返回通过。这是历史覆盖范围，不是豁免普通回复质量的产品决定。
现由同一 Planner 在最终动作和 idle 仲裁后，为普通承接绑定第四种正向合同：
`action / sourceTurnId / sourceText / allowIdle / evidence`。已有身份、情绪支持和修复
合同保持优先，不增加第二个 Planner、判定 provider、重试层或状态流程。

- preflight 用独立本轮来源核对 turn、原文、非空证据及既有 `allow_idle` 决定；普通
  姿态仍由原规则决定。缺失合同不得绕过门控，合同也不自行授予提问许可。
- 生成与判定共享按当前计划裁剪、再清理的有限历史；主动问候前的旧话题只有当前用户
  明确续聊时才进入两侧。判定同时核对计划、合同绑定和候选逐字证据。
- 对个人困扰，回应服务用户当前体验、在意与需要。自然邀请、有用途确认、不追问的
  有依据回应均可独立完成；不要求复述情绪、新事实、建议或固定理想句。
- 合理、相称的隐含情绪理解继续允许，不要求同词或句句保留词，当前纠正/否认优先。
  无依据猜心、编造事件/原因/历史/动机/需要，无用途复述和无用途外围调查不满足合同；
  必要指代澄清、用户实际请求所需事实仍允许，不用关键词硬拦。
- 只有 Planner 已判定 `allowIdle=true` 时，简短收悉可完成当前轮；不能从候选措辞
  自行推导 idle。`questionPolicy=none` 的语义索取即使没有问号也按硬失败处理。
- 每个候选继续经过既有门，同一冻结计划最多生成两稿。默认判定 provider 每稿最多
  一次结构/证据修复，因此最多四次判定请求；自定义离线 provider seam 不重试。
  两稿硬失败则 `FAILED/constraint_failure`，坏稿可留作内部诊断，但提交入口在数据库
  事务前拒绝，生产消息层只返回系统状态，不能提交为助手消息。

离线固定 verdict 只证明上述接线与保护，不证明真实模型能可靠识别这些语义边界。

### 1.2 情境性接纳（2026-10-15 用户批准，本地接线修正）

复用 Planner 的 `ResponsePlan.stance`，仅为既有普通承接与情绪支持动作绑定同一情境性接纳立场；Surface 通过现有 stance 投影收到它，现有语义门和再生成指导复用同一边界。不新增动作、分类器、模型调用或判定层，不启用重构或身体练习。

- 用户表达个人困扰时，可以接纳其在已表达处境中的感受及其已说信息之间的关系，不要求先辩解或否定感受。该回应可以完成普通承接或自然邀请分支中的有依据回应，但不能替代其他已选支持功能。
- 独立说“很正常、没关系”或换词复述仍不足以完成功能；这些词也不构成情境性接纳的禁词。
- 接纳感受不等于认可行为、替第三方定责、保证结果或确认隐藏心理。现有证据、纠正、拒绝、直接任务及提问边界保持有效；不强制先复述情绪、再提问。

## 2. 决策所有权

### 2.1 Response Planner

Response Planner 是正向功能的唯一决策者。每个相关 ResponsePlan 必须在生成前确定：

- 当前动作的证据目标；
- 必须完成的正向功能；
- 允许的可选延续；
- 完成条件；
- 禁止越过的边界。

Planner 不生成用户可见句子，也不选择 Hill 目标或技术。

### 2.2 Clinical compatibility advice

旧 Clinical advice 只能为 Planner 已选择的普通情绪或行动需要提供兼容性边界。它不能
把 `empathic_reflection` 之类的抽象意图直接当成 Surface 可执行功能，也不能成为第二
决策者。

普通关系修复继续不调用旧 Clinical advice。

### 2.3 Surface

Surface 只实现 ResponsePlan 已选择的正向功能。它不能：

- 自行选择支持方式；
- 用更重情绪制造共情；
- 用提问、建议、暂停、在场承诺或安慰替代计划功能；
- 因为语言更自然就改变动作或证据边界。

### 2.4 Validator

Validator 只判断计划功能是否完成和边界是否违反。它不能重新规划，也不能把固定词
是否出现当成功能本身。

实现采用唯一的 Planned Function Semantic Validation Boundary：只要 frozen
`ResponsePlan` 含 handoff 或 positive-function contract 就调用一次 strict JSON 语义门。
handoff 与 positive function 各自 exact-bind、各自提供 exact UTF-16 candidate evidence，
并在两支同时存在时取 AND；不存在的分支必须为 null。旧 handoff Validator 仅为兼容
委托，不保留第二套判断或第二次模型调用。

判定规则的发送范围（2026-10-09 用户批准；功能标准不变）：按冻结计划中实际存在的
handoff / positive-function binding 选择适用规则。情绪支持只发送所选支持功能的完整
要求、适用的 ES 规则和判断功能互斥所需的简短对照；身份/修复只发送所选 mode 的完整
要求，交接只发送当前交接功能的适用细则。共同反注入、exact schema/binding/evidence、
question policy 与失败关闭要求继续保留。双绑定保留各自完整要求并取 AND。既有观察
与剩余整体结论的职责、观察结构及汇总规则保持不变；本次不增加模型调用、语义重试、
固定回复或词表。缺少拒绝来源时仍保留两种来源的既有语义要求。

   隐含情绪，不要求用户说出相同的情绪词。理解应贴住当前对象与处境、不夸大强度或
   持续时间、不编造原因或历史，不把推测说成对用户真实内心的确定结论；用户的明确
   否认或纠正优先。不强制每句加“可能”，也不凭“确实”或“可能”一个词判定。
   对完整回复判断理解是否合理、是否留下可纠正的空间。日常共情式的情境评价不因
   带有情绪词就失败；无依据的理解也不因加了保留词就通过。
   `ES-AFFECT-EVIDENCE` 继续负责无依据、过度确定或夸大的情绪归属；独立原因、事件、
   历史编造仍由原有适用规则处理，不混作新增情绪类别。此前 2026-09-29 C2 A2 的
   “用户未确认任何新类别即拒绝”标准由本条取代；旧用例、标签和历史失败结果封存，
   不追溯改成通过。
   关系影响观察的判定落实（2026-10-10 用户批准修正）：合理、相称且贴住当前对象与处境的
   日常会话情绪理解应为 `none`；“有依据”不要求逻辑必然、唯一可能情绪或逐字命中。
   陈述式承接、没有保留词本身不等于声称洞悉真实内心。用户否认/纠正、真实无依据或内心
   定论、实际强度升级仍按原规则拒绝；此解释不豁免独立的原因、事件或历史编造。
   当前互动的抱怨或负面评价本身可提供会话语境依据，不因没有情绪名称就当作中性事实；
   但负效价不支持任意负面情绪。若某种情绪归属必须补入用户未提供的另一项忧虑、威胁、
   事件、动机或历史才成立，仍为无依据；不把此会话理解新增为 Planner 已确认事实。
   情绪类别有依据与助手是否越权声称知道用户真实/隐藏内心，分别判断；类别合理也不豁免
   后者。按助手实际作出的完整声明判断，复述用户明说内容、引用或否定他人说法、谈助手
   自己的错误，不因出现“知道”等字样而触发；整体边界拒绝不能替代这项情绪观察。
2. **一个可识别的支持功能**：Planner 必须从以下功能中选择恰好一个主要功能：
   - `reduce_expression_burden`：明确用户不需要说明原因、组织完整叙述或一次讲清；
   - `return_focus_control`：允许用户只触及自己当前最想表达的已知部分；
   - `return_amount_control`：允许用户决定表达多少，不索取完整经过；
   - `acknowledge_current_relational_impact`：仅在用户当前挑战助手、但没有足够相邻证据
     形成正式修复目标时，承认当前关系影响和信息边界，不宣称已经修复；
   - `invite_optional_sharing`：按当前对话需要作有依据的回应、确认理解或自然邀请展开；
     可以直接邀请，也可以不追问，不要求先复述情绪（2026-10-10 用户澄清，见下文）；
   - `respect_declined_sharing`：用户不想说或不想被问时，自然回应用户的边界或感受并
     尊重这个拒绝，不邀请、不提问，也不给“想说多少、说哪部分”这类表达许可；允许一句
     不要求回应的倾听表态（2026-10-01 用户产品决定，2026-10-04 修正，见下文）。

纯收悉或在场表态不构成上述支持功能。`invite_optional_sharing` 的直接邀请若在当前
对话中自然打开表达空间，可以独立完成功能，不以先复述感受为前提；其他功能的边界不变。

Planner 选择上述功能时必须使用当前轮证据，而不是把 `return_focus_control` 作为情绪
支持的默认值：显式“不分析／不解释原因”优先选择 `reduce_expression_burden`；显式
“说不清／不想多说”选择 `return_amount_control`；没有正式修复目标的助手关系挑战选择
`acknowledge_current_relational_impact`。只有当前轮存在至少两个不同的情绪或关系影响
证据目标时，才能选择 `return_focus_control`。单一情绪证据默认选择
`invite_optional_sharing`（2026-10-01 起；此前默认 `return_amount_control`），不得
制造“选哪一部分”或 A/B 选择任务，也不得把邀请写成必须继续或必须回答。

情形）：

- 按当前对话需要直接承接具体处境、作有依据的回应或自然邀请展开，可以不追问；
  不设“先复述情绪，再开放追问”的顺序。单句可拒绝的邀请可以独立起作用。
- 2026-10-10 用户澄清：已说被领导批评后，“愿意说说发生了什么吗”仍可邀请展开。
  “听起来你今天不太高兴”在该例只是复述明示情绪、没有实际承接；整句可因质量不足
  拒绝，但不能把后句定为必然重复索取。确认理解等场景中的复述仍可有用；不禁用
  “听起来”，也不靠换情绪近义词或机械重复事件过关。无需每句增加新事实、深层解释
  或建议，更不能为显得有增量而编造内心。

- 2026-10-12 用户中心目标补充：用户在表达个人困扰时，回应和可选追问的用途应贴住
  用户此刻自己的体验、在意与需要，以其已经表达的内容和关系为依据，不替用户确定
  未表达的情绪、价值、动机或需要。收集场合、事情经过或他人反应，本身不构成有用回应；
  用户实际问题或指代歧义确实需要这些事实时，仍允许澄清。跟随当前请求、纠正和拒绝，
  不把客观话题强行转为情绪探索。自然邀请、有用途的理解确认和不追问的回应继续允许。
  判定时区分“偏离用户当前关切”和“把已知事件当未知”：前者若没有实际范围或情绪
  违规，由整体功能结论说明缺少什么作用，不借用 `ES-SCOPE` 或 `affectDrift`。
  此目标同步用于普通承接的 Surface 指导与 §1.1 新增正向合同/语义门；不能用邀请分支
  或普通承接分支的模拟判定证明真实质量通过。
- 不授权连续追问、要求详细经过、替用户推断原因或无依据、过度确定的情绪归属。用户已说出具体事件时，
  可以自然邀请继续展开或澄清有用的未知点；事件梗概已知不等于叙述已完成。仍拒绝
  无视已知事实、声称用户未提供并要求重新确认已答信息的追问，不按具体问句禁问。
- 用户本轮明确不想说、不想被问，或上一轮用户说过且本轮没有明确重新打开（如
  “你问吧”）时，`questionPolicy=none`，原选的 `invite_optional_sharing`、
  `return_amount_control` 或 `return_focus_control` 改为 `respect_declined_sharing`，
  合同证据记录 `sharingInvitationUnavailable=<原因>`（同日第二项用户决定：拒绝时
  不再给表达量许可）。用户自己明确选择的 `reduce_expression_burden`（如“不想讲原因”）
  和关系影响承认不改；“不想多说”表示只说一点，仍是 `return_amount_control`。

## 4. `repair_previous_wording` 正向合同

### 4.1 修复目标类型

Planner 必须在计划中明确修复目标属于哪一种：

- `factual_replacement`：助手弄错人物、事实或用户已经明确给出替代事实；
- `proposition_withdrawal`：助手加入了用户拒绝的情绪、强度、意图或解释；
- `interaction_move_withdrawal`：助手进行了用户拒绝的建议、提问、套话或话题切换。

没有 active handoff 时，若修复来源是已采纳的 `challenges_move_fit`
（`repairState.sourceRelation = "challenges_move_fit"`，采纳条件见交接合同 §6.2
“Ordinary move-fit repair”），Planner 固定选择 `interaction_move_withdrawal`，
`replacementFact` 为空，子类型沿用上述相邻证据规则。无法确定子类型时，仅在独立
preflight 快照从当前用户原文、已采纳解释及相邻已提交来源重新核实既有 0.93 门槛、
最新 saved Assistant 目标、有效且明确为空的 claims 后，允许保持 null 并修复完整目标
回应；并存的来源元数据任一无效或 claims 非空都不能授权。合同中的会话、用户回合及
原文、助手目标及原文必须与快照逐项一致。计划自己的标签或 evidence 字符串不能授权。
来源缺失、过期、错位或不合法仍由 preflight 失败关闭；不编造子类型、不伪造 handoff、
不降级为 `proposition_withdrawal` 或 `factual_replacement`，不降低置信度门槛。纠正具体
事实主张不走此来源。此为2026年10月24日明确调整的未分类修复合同，原实测FAIL保留。

合法空子类型路径沿用4.2及4.3的完成要求：承担并撤回具体目标回应，不以泛泛道歉、
辩护、重复被拒内容、追问或新建议代替修复；不要求用户替助手诊断错误。既有五类子类型
和 typed handoff 的专有授权不变。

Surface 不得自行推断修复类型。

### 4.2 所有修复的共同必需功能

- 明确把错误归于助手自己的上一行动、判断或措辞；
- 不辩护，不归咎用户，不要求用户诊断助手；
- 不宣称关系已经修复；
- 遵守 `questionPolicy`；
- 修复完成前不推进其他目标。

### 4.3 各类型的完成条件

#### `factual_replacement`

明确承担错误，并采用用户当前明确给出的替代事实，即可完成修复。此类回复不强制
额外出现“收回、撤回、不该”等固定词。

仅说“弄错了”而没有替换事实，或替换事实并非用户确认，均不完成。

#### `proposition_withdrawal`

必须明确撤回、否定或停止沿用被拒绝的命题。只有“理解偏了、用词重了、抱歉”而没
有处理具体命题，不完成修复。

#### `interaction_move_withdrawal`

必须明确停止或撤回被拒绝的互动动作，并恢复用户已经明确的当前主题或边界。只有
道歉、继续追问、换一个建议或重复“我会听”均不完成。

### 4.4 修复后的动作边界

修复状态排除并发情绪支持和行动支持。只有 ResponsePlan 独立包含一个仍待完成的普通
话题动作时，Surface 才能在完成修复后实现该动作；否则回复应在修复完成处停止。

## 5. Validator 功能判断合同

Validator 后续实现必须满足：

- 按完整当前语境比较回复中的情绪归属、强度和作用对象，不要求情绪词相同，不维护无限扩张的坏词表；
- 区分独立安慰和附着于表达选择的许可；
- 区分事实替换、命题撤回和互动动作撤回；
- 接受“承担错误＋用户确认替代事实”的事实型修复；
- 拒绝只有空泛承担、没有处理修复目标的回复；
- 一个输出可以同时报告多个真实功能失败，但不能用错误失败码掩盖真正原因；
- regeneration 仍使用同一个 ResponsePlan，不得重新解释或另选目标。

以上合同现由通用 positive-function verdict 覆盖，包括 identity 三种 mode、本节四种
support function 与 repair 三种 mode。malformed、extra/missing key、binding/evidence
mismatch、uncertain 和 provider failure 均 fail closed。该 verdict 不能改变 Safety、
Grounding、结构 preflight 或 question policy，也不能授予提问权限；正向功能是否完成不再
由中文完成短语或正则词表证明。

判定调用失败时，另外记录脱敏类别 `providerFailure = { category, call }`：
- `category` 为 `timeout | rate_limited | provider_5xx | provider_4xx | unknown | prompt_rejected`；
- `call` 为 `initial`（首次调用）或 `schema_repair`（结构修正调用）；由按外发调用计数得出，不包装、不改变抛出的错误；调用方注入的判定器抛错时为 `null`。

分类规则与执行失败审计共用同一函数：
- 本地包装的 502（空回复、网络错误、不支持的响应格式）没有服务商状态码，记 `unknown`，不能作为服务商 5xx 的证据；
- 原始错误信息和响应正文不记录；
- 产品行为不变：仍 fail closed、仍按同一计划再生成、仍记 `GENERATION_NONCONFORMANT`；
- 基础设施重跑资格规则也不变。
