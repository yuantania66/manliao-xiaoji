# Cursor 首版上线交付任务书

编制日期：2026-09-27。本文是执行安排，不是发布通过证明，也不授权立即部署。

## 可直接粘贴给 Cursor 的总指令

你负责把慢聊小记现有首版整理成可以验收、可以复现的发布候选，并完成权限范围内的上线准备。

先读取本仓库 AGENTS.md、其引用的全局规则、docs/RELEASE_TEST_CHECKLIST.md、相关产品与架构合同，再按本文依赖执行。每阶段开始前冻结 Outcome、Acceptance、Allowed scope、Non-goals、Baseline 和修复预算；验收通过后继续可执行阶段，不在每个文件或常规检查后停下来请求确认。

一个主会话负责范围、集成和最终判定。可以并行安排只读调查、独立复核和不重叠的准备工作；每个文件或重叠子系统同一时间只有一个写入者。不要建立多个竞争实现。

本文沿用前轮评估的首版范围：微信登录/游客、聊天、小记及图片、回看/搜索/日历、观察授权与真实统计、设置/反馈/注销。它不是新的产品裁决；阶段 1 须与用户当前指令和现行合同核对。Web 与共用后端的已有能力必须保持回归通过；若另有已承诺的首版能力，不得凭本文将其排除。

`上线待办.md` 记录了短信暂缓，但当前发布清单仍列有真实短信验证。先核实首版账号范围和现行决定：只有能够证明首版全部承诺路径不依赖短信，并记录有效的延后依据，才可把短信门标为不适用；已有手机号账号注销等依赖未解决时保持 BLOCKED。文档有未解决冲突时，只暂停受影响范围并提交具体决定，不能自行豁免。V2、Composer、P4–P6 新运行时接线和其他实验能力不自动成为首版新增工作；已在主线或生产启用的功能、迁移和必跑回归不能因此删除、关闭或跳过。不得为了上线静默隐藏功能或更改产品、Safety、隐私、架构合同。

保留所有既有未提交改动。先调查，再做最小修改。测试失败不得通过放宽断言、删除案例、改成 mock 或重复调用真实模型来掩盖。每个冻结失败门最多两轮修复；仍失败时停止该门，报告原因及一个建议，继续不依赖它的已授权工作。

用户将本任务交给 Cursor 执行后，本地准备、代码整合、隔离测试和文档同步可以连续推进。生产访问、生产迁移/部署、外部体验包上传、提审/发布以及真实用户数据操作，以 Cursor 当前对话可核实的用户授权及工具权限为准。其他会话或历史文档中的“已授权”不是授权转移，本文也不代替授权。真实模型调用先核对合成数据范围、凭据和已有费用授权；授权已覆盖就继续，确实缺失才请求补充。需要人工、设备或外部权限时，一次列清具体缺项，先完成独立可做的工作。

最终按发布清单报告 GO / NO-GO / BLOCKED。不得把代码存在、旧报告通过、预览成功或 mock 结果当作当前候选已通过。

## 阶段 1：形成可复现的集成基线

**目的：**确定到底要发布哪一份代码，消除旧工作区与较新主线的混合状态。

工作：

1. 核对首版范围及现行合同，记录当前 HEAD、分支、dirty 清单；分别列出源码、文档、生成证据及不应纳入发布的文件。保护未跟踪文件，禁止 `reset --hard`、`clean -fd` 或覆盖式搬运。
2. 核实最新远端主线与最近可验证的部署版本；有权限时更新 Git refs。不能取得最新信息时，明确证据日期与限制。
3. 在独立分支/worktree 中以经核实的主线为基础，逐项吸收当前工作区仍需要的变化。按最终代码和行为比对已整合成果，避免重复 cherry-pick、旧文件覆盖新实现。
4. 检查 Prisma schema、全部迁移及调用方一致性。不修改或删除已应用迁移来消除报错，不对生产运行开发迁移命令。
5. 使用全新隔离 PostgreSQL 验证建库路径，并使用合成数据模拟从已知生产 schema 升级到候选。不能仅凭迁移目录数量宣称兼容。

验收：集成基线有可复现 commit，或有包含所需文件内容、锁文件、迁移、工具版本及校验值的受控快照；仅有文件名列表不算可复现，快照不得包含密钥、真实用户数据或依赖缓存。原工作区保留；迁移历史/校验内容一致；隔离建库和升级回归通过；没有未解释的冲突或功能丢失。此时仍是待验证基线；按发布清单，本地必跑门全部通过后才可形成发布候选。

**依赖规则：**阶段 1 完成前不开始候选功能写入。可以并行只读核对真机资源、人工评审安排和运营材料。

## 执行依赖与并行边界

- 阶段 1 → 阶段 2 → 阶段 3 的本地必跑门；本地门通过后记录待外部验收的候选版本。
- 在同一候选上，阶段 3 的真实模型/人工验收与阶段 4 真机验收可以并行；等待人工不阻止已有设备上的独立验证。阶段 4 先完成下述获授权测试环境部署，不能借用不同版本的旧生产后端。
- 阶段 5 的资料与资源核对在阶段 1 后并行；最终配置、恢复和审核结论必须对应最终候选。
- 阶段 3、4、5 的适用门全部通过后，才进入阶段 6 的生产部署与发布。修复改变候选时按影响更新证据，不把阶段编号当成只能顺序等待的理由。

## 阶段 2：补齐已确认的功能缺口

**目的：**让首版可见功能与真实数据、授权行为一致。

首先在候选上复核缺口是否还存在。直接相关文件为：

- `miniprogram-project/pages/insights/insights.js`、对应 WXML；
- `app/api/insights/route.ts`、`lib/insights.ts`、`app/me/insights/page.tsx`；
- 小程序 API 请求层、`utils/auth.js` 及其直接调用方。

工作：

1. 小程序复用既有统计接口及口径，替换示例数组；覆盖 7/30/90 天、空数据、游客、加载失败和重试。
2. 按现有合同补齐观察授权的撤回/清理路径；账号 A 的授权不能传给账号 B。退出、注销、401、切换账号后，不展示上一账号结果，也不能让晚到响应恢复旧结果。
3. 读取现有授权与数据保留合同，明确授权存储与派生数据处理边界。如合同确实没有决定，先提交一项具体产品决策，不自行引入新的持久化同意系统或改写产品流程。
4. 复用已有请求、身份和清理机制。已实现的微信登录、注销、Web 统计不重复开发。

验收：有可复现的正常、空数据、未授权、撤回、跨账号、401、网络失败及晚到响应回归；授权后展示本人真实统计；退出/撤回后不残留可见结果；Web 与现有注销行为无回归；相关文档同步。

## 阶段 3：完成候选工程与对话验收

**目的：**为同一个候选补齐机器可执行和人工判断的证据。

工作：

1. 先跑修改面的窄门，再在明确命名的隔离数据库运行 `npm run check:release:required`。以当前脚本与 `.github/workflows/ci.yml` 为准核对前置配置，包括 `DATABASE_URL`、`PROACTIVE_COMMIT_TEST_DATABASE_URL`、`PROACTIVE_COMMIT_TEST_ALLOW_DDL`、`CANCEL_ACCOUNT_TEST_DATABASE_URL`；所有数据库目标必须经核实为本次隔离测试库，DDL 开关仅对该库设置。检查脚本的数据目标和副作用，不把开发库或生产库当测试库，也不把缺少前置配置误判为产品失败。
2. 按候选相对部署基线的代码、运行配置、feature flags、模型和 Prompt/schema 变化映射条件门；Chat API/鉴权/持久化等需要时追加 `smoke:local-api`。记录已被综合门覆盖的检查，避免无意义重复；部署基线或配置未知时，相关适用性标为待核实，不能据此标为不适用。
3. 按实际触发范围执行 Safety、Handoff、planned-function、主动消息等真实模型门；Clinical、多轮轨迹、Chat Gate 同样按发布合同判定。固定 provider/model、Prompt/schema/fixtures 和独立重复次数。
4. 准备脱敏盲评材料，交由真实人工评审；记录评审者、规则、结果、分歧及裁决。Cursor 的自评或模型 Judge 不代替人工。
5. 只用获授权的合成案例。真实模型失败按既有重试合同处理，不能反复采样直到出现想要的答案。被首版冻结合同触发的跨自然日稳定性要求必须真实跨日，独立重复不能用一次调用内的重试充数。

验收：本阶段负责的本地必跑门、条件工程门、真实模型门及对话人工门通过，证据绑定候选身份；未触发项说明依据。阶段 4 的真机门、阶段 5 的环境与运维门分别验收，不作为开始它们前必须先通过的阶段 3 条件。缺凭据、费用授权或评审者的项目为 BLOCKED，不能写 PASS；本阶段局部通过不等于最终 GO。

## 阶段 4：完成微信与双端真机主链路

**目的：**证明候选在用户实际设备上可用。

**前置：**本地必跑门通过后，将同一候选部署到获授权的测试/预发布环境，准备合成测试账号与可追溯的体验包。确认环境、合法 HTTPS 域名、后端版本和小程序包版本匹配；外部上传或环境操作只在已有授权范围内执行。该测试部署属于本阶段前置，不必等待阶段 6 的生产发布；没有可用环境时记录 BLOCKED，不默认改用生产测试。

至少覆盖一台 iOS 和一台 Android：

- 编译、预览、HTTPS 合法域名、真实微信登录、游客、重启恢复、token 失效；
- 新建/恢复会话、发送与重试、重复点击、弱网/断网、前后台切换；
- 小记创建/编辑/删除、图片上传与失败提示、历史/搜索/日历；
- 观察授权/撤回与账号隔离、设置/反馈、退出和注销；
- 依据冻结合成案例验证 Safety 路径及删除后数据失效。

验收：每项注明设备/系统、前后端版本、测试日期、预期/实际结果、脱敏证据及缺陷状态。扫码登录一次、浏览器截图或 JS 语法检查均不代替完整真机测试。

Cursor 负责准备步骤、构建包、收集和分析可用证据、修复确认缺陷；真人负责实际设备操作与主观体验判断。没有设备时明确请求所需设备和测试动作，不伪造通过。

## 阶段 5：完成运维与审核准备

**目的：**使发布与故障恢复有明确操作步骤。

阶段 1 后可并行准备文档、核对已有配置；结论必须绑定最终候选。

- 核实主体认证、服务类目、合法域名和证书，以及协议/隐私指引与实际能力一致性；不代替资质或法律判断。
- 在获授权环境检查生产配置和持久上传路径，执行适用的 `audit:prod-env`、`smoke:prod` 并保留脱敏结果；不得输出凭据。显式核对 `PROD_ENV_FILE` 和 `SMOKE_BASE_URL`：前者默认读取本地 `.env`，后者默认请求生产域名；不能在预发布验收中省略目标后把旧生产结果记到候选上。
- 确认数据库与受管媒体的备份范围、恢复步骤、责任人和执行证据；本地演练使用合成数据。未经授权不复制生产数据。
- 准备部署步骤、迁移顺序、应用与数据库兼容性判断、回滚/恢复方案、监控入口、灰度停止条件和故障处置方式；不假设数据库迁移可以直接回滚。沿用已有发布阈值，缺少必要阈值时列为待确认决定。
- 准备版本说明、审核路径、微信登录/游客说明以及必要的审核材料。

验收：有经过核实的部署与恢复方案、配置检查和审核材料；缺失的账号权限、认证、设备或外部状态清楚列明。短信是否排除必须与首版实际路径一致，不能忽略已有手机号用户的注销依赖。

## 阶段 6：授权发布、提审与灰度确认

部署前把待发布 commit、变更摘要、迁移方案、回滚限制、全部验收状态和剩余项整理为一个可审阅结果。

需要授权时只针对尚未授权的具体动作发起一次明确请求；已有授权不重复请求。不得在准备工作未完成前只问“是否继续”。

测试/预发布部署已在阶段 4 前完成；本阶段执行获授权的生产部署、生产复验、微信提审与小范围发布，并分别记录结果。生产复验不得使用旧服务器 Smoke 为新候选背书。

审核通过并获发布授权后，按既定安排小范围发布并观察登录、接口、AI 回复、图片上传失败及关键用户反馈。明确真实观察时段与负责人；不要声称一次检查等于持续监控。需后台监控时另行确认实际调度机制已建立。

验收：候选证据支持发布判定；实际部署版本可核对；新版本复验通过；微信审核/灰度分别有真实结果。外部审核等待写明等待，不能算已上线。

## 证据与交接规则

沿用现有交付台账，仅维护一份本次候选验收记录，不为每次尝试制造新文档。

每条记录至少包含：阶段/门、状态、候选 commit 或源码指纹、环境与配置指纹、命令及退出码、时间、必要的模型或设备身份、证据位置、责任人与外部依赖。未执行的门标为 NOT_RUN/PENDING，不提前宣称通过。

- 候选变化后标记受影响证据失效：模型/Prompt/schema 变化重跑相关真实门；界面/客户端流程变化复验相关真机门；迁移/鉴权/删除变化重验对应隔离与集成门。最终候选仍须通过唯一必跑入口；纯文档变化不要求全部功能证据重跑。
- 只读调查、历史通过、当前候选通过、未运行、BLOCKED、FAIL 必须分开。
- 有明确失败为 NO-GO；无失败但必需外部证据不可用为 BLOCKED；所有适用门通过才可 GO。不要用完成百分比替代判定。
- 工程发布判定与微信审核/实际发布状态分开：工程门 GO 不等于微信审核通过或已上线；平台审核尚在等待时如实记录等待，不回写成某个测试失败，也不能宣称整个交付完成。
- 每阶段结束给出 Completed、Evidence、Remaining、Blocking Reason，必要时只推荐一个下一步。常规验收通过后继续执行，直到全部完成或遇到明确停止条件。

## 本任务书的验收边界

本文交付的是 Cursor 执行顺序、范围与验收要求。它没有执行功能修复、模型评测、生产访问或发布操作。执行者必须在阶段 1 刷新基线；不得把本文的历史观察当作实时生产状态。
